# Техническое задание: калькулятор «Диагностика скрытой выручки бизнеса»

**Версия:** 0.1, для старта в Codex.  
**Цель:** лид-магнит маркетингового агентства и фундамент будущего ИИ-аналитика стратегий.

## 1. Продуктовая модель

Три уровня:
1. **Бесплатно:** экспресс-расчёт по 6–8 отраслевым вопросам, три точки роста, финансово-аналитический дашборд без обязательной передачи контактов.
2. **За контактные данные:** углублённая ИИ-диагностика, загрузка документов, сценарии и персональный PDF-отчёт.
3. **Платно:** экспертная диагностика с участием маркетолога, проверкой данных и индивидуальной дорожной картой; цена определяется отдельно.

Отрасли первой версии:
- услуги и образование (детские центры, сады, школы);
- красота и здоровье (салоны, SPA, студии);
- розница;
- общепит (кафе, рестораны, кофейни и др.).

## 2. Пользовательский путь

Лендинг → выбор отрасли → 6–8 вопросов → финансовый дашборд → предложение расширенной диагностики → согласие и контакты → структурированные вопросы → адаптивные уточнения ИИ → проверка данных → сценарный расчёт → PDF → предложение платной экспертной работы.

Основной интерфейс — сайт. Telegram/MAX используются в дальнейшем для получения отчёта и коммуникаций; интеграции в первой итерации необязательны и должны зависеть от официальных разрешённых API.

## 3. Экспресс-дашборд

Показывать:
- текущую/расчётную выручку и единицы измерения;
- диапазон возможного дополнительного оборота;
- консервативный, базовый, оптимистичный сценарии;
- три главные точки роста с оценкой в рублях и логикой расчёта;
- график сравнения;
- источники и уровень полноты данных;
- предупреждение «сценарий, не гарантия результата»;
- призыв перейти к ИИ-диагностике.

Не публиковать произвольную «сумму потерь», если недостаточно данных.

## 4. Финансовое ядро — главный приоритет

Разработать **детерминированный** расчётный модуль отдельно от языковой модели:
- словарь показателей, единиц, периодов и допустимых диапазонов;
- отраслевые конфигурации входных данных и ограничений;
- прозрачные формулы, например выручка = количество покупок × средний чек; количество покупок из лидов = лиды × конверсия, если исходные метрики корректны;
- отдельные модели: необработанные лиды, конверсия, средний чек, повторные продажи, реактивация базы, загрузка, допродажи, маркетинговые каналы, ограничения по мощности;
- предотвращение **двойного счёта** пересекающихся возможностей;
- сценарное моделирование с понятными предположениями;
- расчёт прироста **прибыли только если имеются сведения о затратах**; иначе показывать прирост выручки и потребность в данных;
- расчёт надёжности как **индикатора качества данных**, а не статистически обоснованной вероятности без модели;
- поддержка ручного ввода и замены предположений пользователя.

Разработать тесты для типовых и пограничных случаев по каждой отрасли: нули, неполные данные, ограничения мест/столов/специалистов, разные периоды, завышенная конверсия, пересекающиеся источники выручки.

## 5. ИИ-аналитик

Два этапа: структурированные обязательные вопросы + адаптивные уточнения по выявленным проблемам. Языковая модель интерпретирует результаты и готовит рекомендации, **не придумывает исходные значения и не меняет формулы**.

Для неподтверждённых показателей — уточняющий вопрос или явно обозначенное сценарное предположение. Не представлять сценарии как отраслевые нормы без подтверждённых источников.

## 6. Загрузка файлов (после первого расчётного MVP)

Форматы XLSX/XLS, CSV, PDF, JPG/PNG. Извлекать показатель, период, единицу, источник; показывать пользователю таблицу для подтверждения/исправления. Некорректные файлы не ломают диагностику, допускается ручной ввод.

Прямых CRM/кассовых/банковских интеграций в первом MVP нет.

## 7. PDF и мини-CRM

PDF: профиль бизнеса, источники данных, экономические показатели, проблемы, возможные резервы, три сценария, рекомендации, ограничения достоверности, предложение экспертной диагностики. Все числа должны поступать из расчётного модуля.

Мини-CRM: клиент, контакты, отрасль, источник, этап, результаты, отчёт, резюме ИИ, статус «новый → диагностика → переговоры → КП → договор». Пользователь может запросить удаление данных; админ видит только разрешённые ему карточки.

## 8. Конфиденциальность и запуск

- Не использовать реальные клиентские файлы в тестах. Обрабатывать данные с учётом законодательства о персональных данных и применимых требований к размещению/передаче данных.
- До запуска с реальными пользователями провести юридическую проверку согласий, политики, хранения и внешних AI-провайдеров.
- Не публиковать продукт и не подключать платные API без разрешения владельца.
- Ключи хранить только в защищённых переменных окружения, не в репозитории.

## 9. Архитектура и этапы

Предпочтительно: простой веб-интерфейс + серверный API + PostgreSQL + отдельная библиотека финансовых расчётов; языковая модель как заменяемый модуль. Codex может предложить более простой вариант с аргументацией.

**Первый вертикальный срез:** одна отрасль → ввод тестовых показателей → три проверяемых сценария → дашборд с происхождением цифр. Затем расширить на остальные три отрасли.

**Следующие этапы:** отраслевые тесты → адаптивный ИИ → импорт файлов → PDF → мини-CRM → мессенджеры → пилот с предпринимателями.

## 10. Критерии первого этапа

1. Есть описание показателей и формул.
2. Есть минимум 10 контрольных расчётов с ожидаемыми результатами, включая ошибочные данные.
3. Отсутствует двойной счёт в выбранных тестовых сценариях.
4. Отчёт показывает исходные значения и предположения.
5. Код запускается и тесты проходят без внешних платных API.
6. Есть README, `.env.example`, `AGENTS.md`, инструкция запуска и перечень нерешённых вопросов.
