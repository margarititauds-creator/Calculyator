ОБЛАЧНАЯ ДОСТАВКА КАЛЬКУЛЯТОРА — ПОДГОТОВКА ИСПРАВЛЕНИЯ
24.11.2026, Екатеринбург

ЦЕЛЬ
Постоянный лид-магнит: посетитель получает расчёт, заявка сохраняется в российской базе и автоматически доставляется владельцу в Telegram независимо от компьютера владельца. Полным завершением считается подтверждённая сквозная отправка и работа повторной доставки, а не включённые переключатели.

НОВОЕ В ЭТОЙ ПРОВЕРКЕ
В Edge консоль Яндекс Облака показывает «Нет соединения с интернетом». После обновления ошибка сохранилась. Владелец отдельно подтвердил, что карточка функции не открывается. Прямой запрос с ПК получает HTTP 200 от адреса консоли и 401 от официального API управления без авторизации. HTTP 200 сам по себе не подтверждает доступность интерфейса: полученный публичный ответ содержит загрузочную логику авторизации, а не карточку ресурса.
Windows сообщает наличие интернета, Happ остаётся включён. Прокси Windows и HTTP(S)_PROXY не настроены. Эти проверки не устанавливают точную причину сбоя браузерной сессии.

ПОДГОТОВЛЕННЫЙ ВАРИАНТ ПРОВЕРКИ
Добавить только один маршрут POST /internal/telegram-delivery в существующий API Gateway, направленный на существующий обработчик Sites. Затем проверить, работает ли соединение через API Gateway. Это гипотеза для проверки; отличный от функции выходной IP и успешность маршрута пока не доказаны.
Публичная документация API Gateway поддерживает HTTPS-интеграцию http с фиксированным URL, передачей именованных заголовков и ограниченными тайм-аутами:
https://yandex.cloud/ru/docs/api-gateway/concepts/extensions/http
https://yandex.cloud/ru/docs/api-gateway/concepts/networking

ПОДГОТОВКА НА ПК
Файл serverless/scripts/prepare-gateway-relay.mjs принимает актуальный JSON-экспорт шлюза и создаёт новую спецификацию. Он проверяет идентификатор функции приёма, не заменяет существующие маршруты, отказывается работать при конфликте маршрута и не перезаписывает существующий выходной файл.
Назначение фиксировано: тот же защищённый обработчик калькулятора на Sites. Передаются только Content-Type, Accept, User-Agent и два заголовка существующей HMAC-подписи. Секрет и токен бота в спецификацию не добавляются; авторизация остаётся у обработчика. Произвольного адреса назначения и пересылки всех заголовков нет.
Новые тесты проверяют сохранность исходной спецификации, отказ для чужого шлюза/конфликта и ограниченность маршрута. Общая команда node --test test/*.test.js: 53 теста прошли. Это локальные проверки конфигурации и приложения; они не подтверждают работу сети провайдера.

ПОРЯДОК ПРИМЕНЕНИЯ ПОСЛЕ ВОССТАНОВЛЕНИЯ ДОСТУПА
1. Экспортировать актуальную спецификацию существующего шлюза и сохранить закрытую резервную копию. Не подменять её старым шаблоном.
2. Подготовить и сравнить новую спецификацию: единственное изменение — дополнительный маршрут.
3. Проверить подписанную операцию check без анкет через новый маршрут. Проверить, что неподписанный запрос не вызывает отправку.
4. Только при подтверждении правильного бота переключить существующий облачный отправитель на адрес шлюза. Новые ключи, серверы и локальные задания для этого не требуются. Платный режим не включать.
5. Отправить вымышленную анкету через опубликованную форму. Проверить шифрованную запись, сообщение с расчётом и контактом в Telegram, сохранённый messageId и статус delivered.
6. Отдельно подтвердить повторную облачную доставку таймером без запуска локального worker. Возвращать в очередь недоставленные реальные анкеты только после работоспособности маршрута и проверки действующего согласия.
7. Если маршрут не работает, вернуть только изменённую конфигурацию из резервной копии. Не объявлять решение успешным и не удалять сохранённые заявки.

ТЕКУЩИЙ СТАТУС
Подготовка и локальные тесты выполнены. Маршрут в облако не загружен: доступ к управлению Яндекс Облаком в браузере пока не восстановлен. Полноценная облачная доставка не подтверждена. Рабочие функции, таймер, сайт, DNS, ключи и политика обработки не изменены. Резерв на ПК не используется как замена требуемой круглосуточной работе.
